# 麦当劳周末规划师

## 这个 skill 做什么

把「周末不知道干嘛」变成一个可执行的时间表。输入一个城市，输出一份单页 HTML：门店分布、四个时间点的路线、汉堡拆解、券池拼单表。

关键分工：

- **数字全部来自 MCP**：门店编码、地址、营业时间、价格、券、活动，一个都不能编。
- **判断由你来写**：哪几家店值得去、时间怎么排、这条街几点熄灯、这个片区的麦麦和城区有什么不同。这是页面里唯一无法自动化的部分，也是它比攻略网站强的地方。

## 执行流程

### 第 1 步：确认输入

需要两个信息：

| 信息 | 来源 | 缺失时 |
|---|---|---|
| 城市 | 用户输入 | 直接问，不要猜 |
| 片区 / 商圈关键词 | 用户输入，或你按城市推断 | 用该城市最典型的 2 个片区（一个市中心 + 一个郊区/卫星城） |
| 预算 | 可选，默认人均 20–30 元 | 用默认值 |

片区关键词决定门店质量。用商圈名、地标名、大学名、地铁站名，不要用「XX 区」这种行政区划 —— 接口按关键词匹配门店名和地址，行政区名会召回一堆无关门店。

参考关键词：广州「天河」「从化」、北京「五道口」、上海「五角场」、成都「春熙路」、深圳「科技园」「龙岗」、杭州「武林」「下沙」、武汉「光谷」「江夏」。

产出 1 个片区也可以，但 2 个片区（城区 + 郊区）能撑起「农村的麦麦有什么不一样」这个最有意思的对比。默认做 2 个。

### 第 2 步：拉真实数据

按顺序调用，详细参数和返回值见 `references/mcp-recipes.md`：

> `mcp__mcd-mcp__*` 是延迟加载工具，先用 ToolSearch 取 schema，再 DeferExecuteTool 调用。

```
1. now-time-info                     取服务器时间，决定「今天」是哪天
2. query-nearby-stores  × 片区数       searchType=2 + city + keyword，每个片区取前 5 家
3. query-meals  × 每个片区的首店       拿真实菜单价（同一商品不同店价格不同）
4. query-meal-detail × 3             巨无霸 1100 / 龙焰鸡腿堡 521952 / 随心配 9900013304
5. available-coupons                 当前可领券（写进页面右侧券卡）
6. query-store-coupons × 首店         该店真正可用的券（用来写「券的围栏」那条实测）
7. campaign-calendar                 活动时间线
8. calculate-price                   验证券池与套餐实付价
9. list-nutrition-foods              汉堡营养（可选，不调用就用默认值）
```

硬性要求：

- 每个片区 **至少 5 家门店**，少于 5 家就换关键词重查。
- 价格必须来自 `query-meals` 或 `calculate-price` 的返回，不要用记忆里的价格。
- 券必须来自 `available-coupons`。卡包为空是常态，如实写「当前可领 N 张」，不要假装有券。
- 某家店 `businessStatus=false` 时，`closed: true` 并在 tags 里标「当前暂停营业」。

### 第 3 步：写 plan.json

字段说明见 `references/data-schema.md`，完整样例见 `references/example-plan-guangzhou.json`（广州两片区，可直接复制改）。

写文案时的判断标准：

- `cities.*.insights` 三条，每条都必须**基于拉到的数据**。好例子：「4 / 5 家通宵，说明这个片区的夜间人流由地铁末班车和夜班楼撑着」。坏例子：「天河很繁华，适合逛街」。
- `cities.*.route.steps` 四个时间点，时间要能对上营业时间。路线里至少两家店，且给出的门店编码必须真实存在。
- `cities.*.escape` 是「想逃离」方向。核心是**算清最后一班车 / 最后一家店关门时间**，不是再写一条普通路线。
- `cities.*.note` 写一句反常识的提醒（最晚闭店、暂停营业、末班车）。

### 第 4 步：构建页面

```bash
python scripts/build.py --data plan.json --out <输出路径>
```

Windows 上没有 `python` 命令时，用托管解释器：
`C:\Users\minttt\.workbuddy-ai\binaries\python\envs\default\Scripts\python.exe`

输出路径默认 `./outputs/mcd-weekend-<城市拼音>.html`。构建脚本会校验 schema，缺字段会直接报错并指出路径，按提示补。

构建成功后用 `present_files` 打开页面。

### 第 5 步：交付说明

回复里给出：几个片区几家店、通宵店占比的对比、券池在 3 人时的实际人均、以及一句「券是可领状态、卡包里还没有」的诚实提醒。

## 硬性约束

- **不编数据**。门店、编码、价格、券、活动一律来自 MCP 返回。MCP 调用失败就如实告诉用户哪一步没拿到，不要用「大概 25 元左右」糊过去。
- **不改模板**。样式、结构、交互都在 `assets/template.html` 里，改数据只动 plan.json。确实要调样式再改模板，改完跑一遍 `build.py` 验证。
- **券池计算依赖前 3 张券的顺序**：`coupons[0]` 是堡券、`coupons[1]` 是炸鸡/双人券、`coupons[2]` 是免费小食券。顺序错了券池表就会算错。
- **页面不联网**。产出是单文件，所有数字是抓取时刻的快照，回复里要说明这一点。

## 常见问题

**门店数量不够 5 家**：关键词太窄。换成更大的商圈名，或改用 `searchType=2` 带城市名 + 区名。

**同城不同店价格不一样**：这是真实情况，不要抹平。把它写进 `priceNote`，并给出双向例子（有贵的有便宜的），结论是「门店有独立定价权限」。

**券全部为空**：正常。`available-coupons` 返回的是「可领」，`query-my-coupons` 返回的是「已有」。卡包空就照实写，页面里那句「领完别急着走」的围栏提示反而更有价值。

**用户只给城市不给片区**：自己挑 2 个，一个市中心商圈 + 一个郊区，并在回复里说明你选的是哪两个、为什么。
